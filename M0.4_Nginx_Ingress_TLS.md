## Overview

This module sets up the front door for every web interface in the AML-SIEM platform. Without it, clients can only access dashboards via raw IP addresses and port numbers — which is unusable, insecure, and unprofessional. After this module every service will be reachable at a clean HTTPS URL like `wazuh.chemdry.amlsiem.com` with a valid TLS certificate.

### What gets installed

| Component | Role |
|---|---|
| **Nginx Ingress Controller** | Receives all incoming HTTPS traffic and routes it to the correct internal service based on hostname |
| **cert-manager** | Automatically requests, issues, and renews TLS certificates from Let's Encrypt — zero manual certificate work |
| **ClusterIssuer** | The cert-manager configuration that tells it to use Let's Encrypt's production servers |
| **Wildcard DNS** | `*.CLIENT.amlsiem.com` pointing to your VM's IP — one DNS entry covers all subdomains for a client |

### Why disable K3s's built-in Traefik?

K3s ships with Traefik as its default ingress controller. You are replacing it with Nginx because:
- Nginx has more predictable configuration syntax
- The AML-SIEM runbook and all Sprint manifests are written for Nginx annotations
- Nginx handles high-volume log dashboard traffic more predictably than Traefik

Traefik must be disabled before Nginx is installed — they cannot both listen on ports 80 and 443 simultaneously.

Estimated time: 30–40 minutes (plus DNS propagation time which can take up to 30 minutes).

## Step 2 — Disable K3s Built-in Traefik

K3s installs Traefik by default. Disable it permanently so it does not restart after reboots.

### 2.1 — Delete the Traefik HelmChart resource

```bash
KUBECONFIG=~/.kube/config kubectl delete helmchart traefik -n kube-system 2>/dev/null || echo "Traefik helmchart not found — OK"
KUBECONFIG=~/.kube/config kubectl delete helmchart traefik-crd -n kube-system 2>/dev/null || echo "Traefik-crd not found — OK"
```

### 2.2 — Disable Traefik in K3s config

```bash
sudo mkdir -p /etc/rancher/k3s/config.d

cat << 'EOF' | sudo tee /etc/rancher/k3s/config.yaml
disable:
  - traefik
EOF
```

### 2.3 — Delete existing Traefik pods and services

```bash
KUBECONFIG=~/.kube/config kubectl delete deployment traefik -n kube-system 2>/dev/null || true
KUBECONFIG=~/.kube/config kubectl delete service traefik -n kube-system 2>/dev/null || true
KUBECONFIG=~/.kube/config kubectl delete service traefik-web -n kube-system 2>/dev/null || true
KUBECONFIG=~/.kube/config kubectl delete service traefik-websecure -n kube-system 2>/dev/null || true
```

### 2.4 — Confirm Traefik is gone

```bash
KUBECONFIG=~/.kube/config kubectl get pods -n kube-system | grep traefik
```

Expected: no output — no Traefik pods running.

## Step 4 — Install Nginx Ingress Controller

### 4.1 — Add the Nginx Ingress Helm repository

```bash
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
```

### 4.2 — Create the ingress-nginx namespace

```bash
KUBECONFIG=~/.kube/config kubectl create namespace ingress-nginx 2>/dev/null || echo "Namespace already exists"
```

### 4.3 — Install Nginx Ingress via Helm

```bash
KUBECONFIG=~/.kube/config helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --set controller.service.type=LoadBalancer \
  --set controller.service.externalTrafficPolicy=Local \
  --set controller.config.use-forwarded-headers="true" \
  --set controller.config.proxy-body-size="50m" \
  --set controller.config.proxy-read-timeout="3600" \
  --set controller.config.proxy-send-timeout="3600" \
  --wait \
  --timeout=5m
```

**What these settings do:**

| Setting | Purpose |
|---|---|
| `service.type=LoadBalancer` | Exposes Nginx on a public IP via K3s's built-in load balancer (ServiceLB) |
| `externalTrafficPolicy=Local` | Preserves real client IPs in access logs |
| `use-forwarded-headers` | Correctly handles `X-Forwarded-For` headers from upstream proxies |
| `proxy-body-size=50m` | Allows file uploads up to 50MB — needed for TheHive evidence attachments |
| `proxy-*-timeout=3600` | Long timeouts for Wazuh dashboard queries that can run for minutes |

### 4.4 — Verify Nginx is running

```bash
KUBECONFIG=~/.kube/config kubectl get pods -n ingress-nginx
```

Expected — all pods `Running`:

```
NAME                                        READY   STATUS    RESTARTS   AGE
ingress-nginx-controller-xxxxx-xxxxx        1/1     Running   0          60s
```

### 4.5 — Get the LoadBalancer external IP

```bash
KUBECONFIG=~/.kube/config kubectl get service ingress-nginx-controller -n ingress-nginx
```

Expected:

```
NAME                       TYPE           CLUSTER-IP     EXTERNAL-IP      PORT(S)
ingress-nginx-controller   LoadBalancer   10.43.x.x      34.XXX.XXX.XXX   80:xxxxx/TCP,443:xxxxx/TCP
```

> On GCP with K3s's ServiceLB, the EXTERNAL-IP should match your VM's public IP. If it shows `<pending>` for more than 2 minutes, see the troubleshooting section.

## Step 5 — Configure DNS

This is a manual step done in your domain registrar or DNS provider (Cloudflare, Route 53, GCP Cloud DNS, etc.).

### 5.1 — Add DNS A records

You need to add the following A records pointing to your VM's external IP (`34.XXX.XXX.XXX`):

| Record Type | Name | Value | TTL |
|---|---|---|---|
| A | `aml-lab.amlsiem.com` | `34.XXX.XXX.XXX` | 300 |
| A | `*.aml-lab.amlsiem.com` | `34.XXX.XXX.XXX` | 300 |
| A | `test.aml-lab.amlsiem.com` | `34.XXX.XXX.XXX` | 300 |

The wildcard record `*.aml-lab.amlsiem.com` covers:
- `wazuh.aml-lab.amlsiem.com`
- `grafana.aml-lab.amlsiem.com`
- `thehive.aml-lab.amlsiem.com`
- `shuffle.aml-lab.amlsiem.com`
- Any other subdomain you add later

> For future clients, add `*.chemdry.amlsiem.com → 34.XXX.XXX.XXX` etc.

### 5.2 — Open ports 80 and 443 in GCP firewall

Go to **GCP Console → VPC Network → Firewall → Create Firewall Rule:**

**Rule 1 — HTTP:**

| Field | Value |
|---|---|
| Name | `aml-siem-allow-http` |
| Direction | Ingress |
| Action | Allow |
| Source | `0.0.0.0/0` |
| Protocols/ports | TCP 80 |

**Rule 2 — HTTPS:**

| Field | Value |
|---|---|
| Name | `aml-siem-allow-https` |
| Direction | Ingress |
| Action | Allow |
| Source | `0.0.0.0/0` |
| Protocols/ports | TCP 443 |

Also open in UFW on the VM:

```bash
sudo ufw allow 80/tcp comment 'HTTP for Let Encrypt + redirect'
sudo ufw allow 443/tcp comment 'HTTPS for all web interfaces'
sudo ufw status
```

### 5.3 — Verify DNS propagation

Wait 5–30 minutes after adding records, then verify:

```bash
# Check DNS resolution
dig aml-lab.amlsiem.com +short
dig test.aml-lab.amlsiem.com +short
```

Both should return your VM IP. If empty — DNS has not propagated yet. Wait and retry.

```bash
# Also verify port 80 is reachable
curl -v http://test.aml-lab.amlsiem.com 2>&1 | head -20
```

## Step 6 — Install cert-manager

cert-manager runs inside K3s and automatically requests TLS certificates from Let's Encrypt whenever a new Ingress resource is created.

### 6.1 — Add the cert-manager Helm repository

```bash
helm repo add jetstack https://charts.jetstack.io
helm repo update
```

### 6.2 — Create the cert-manager namespace

```bash
KUBECONFIG=~/.kube/config kubectl create namespace cert-manager 2>/dev/null || echo "Namespace exists"
```

### 6.3 — Install cert-manager via Helm

```bash
KUBECONFIG=~/.kube/config helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --set installCRDs=true \
  --wait \
  --timeout=5m
```

`installCRDs=true` installs the Custom Resource Definitions that cert-manager needs — Certificate, ClusterIssuer, CertificateRequest, etc.

### 6.4 — Verify cert-manager pods are running

```bash
KUBECONFIG=~/.kube/config kubectl get pods -n cert-manager
```

Expected — all three pods `Running`:

```
NAME                                      READY   STATUS    RESTARTS
cert-manager-xxxx                         1/1     Running   0
cert-manager-cainjector-xxxx              1/1     Running   0
cert-manager-webhook-xxxx                 1/1     Running   0
```

## Step 7 — Create Let's Encrypt ClusterIssuer

The ClusterIssuer tells cert-manager how to request certificates — which CA to use (Let's Encrypt), what challenge type (HTTP-01), and what email address to register with.

### 7.1 — Create the ClusterIssuer manifest

```bash
cat << 'EOF' > /tmp/clusterissuer.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@amlakalarabia.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
    - http01:
        ingress:
          class: nginx
EOF
```

> Replace `admin@amlakalarabia.com` with your actual email. Let's Encrypt sends expiry warnings to this address.

### 7.2 — Apply the ClusterIssuer

```bash
KUBECONFIG=~/.kube/config kubectl apply -f /tmp/clusterissuer.yaml
```

### 7.3 — Verify the ClusterIssuer is ready

```bash
KUBECONFIG=~/.kube/config kubectl get clusterissuer letsencrypt-prod
```

Expected:

```
NAME               READY   AGE
letsencrypt-prod   True    30s
```

`READY: True` means cert-manager successfully registered with Let's Encrypt.

If it shows `False` after 2 minutes:

```bash
KUBECONFIG=~/.kube/config kubectl describe clusterissuer letsencrypt-prod
```

Look at the `Status` section for the error message.

## Step 8 — Deploy a Test Ingress with TLS

This test creates a real Ingress resource for `test.aml-lab.amlsiem.com` pointing at a simple nginx pod. cert-manager will automatically request a Let's Encrypt certificate for it.

### 8.1 — Deploy a simple test pod and service

```bash
cat << 'EOF' > /tmp/test-app.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: aml-lab
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: test-app
  namespace: aml-lab
spec:
  replicas: 1
  selector:
    matchLabels:
      app: test-app
  template:
    metadata:
      labels:
        app: test-app
    spec:
      containers:
      - name: nginx
        image: nginx:alpine
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: test-app
  namespace: aml-lab
spec:
  selector:
    app: test-app
  ports:
  - port: 80
    targetPort: 80
EOF

KUBECONFIG=~/.kube/config kubectl apply -f /tmp/test-app.yaml
```

### 8.2 — Create the Ingress with TLS and HTTP redirect

```bash
cat << 'EOF' > /tmp/test-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: test-ingress
  namespace: aml-lab
  annotations:
    kubernetes.io/ingress.class: nginx
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
spec:
  tls:
  - hosts:
    - test.aml-lab.amlsiem.com
    secretName: test-aml-lab-tls
  rules:
  - host: test.aml-lab.amlsiem.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: test-app
            port:
              number: 80
EOF

KUBECONFIG=~/.kube/config kubectl apply -f /tmp/test-ingress.yaml
```

**Key annotations explained:**

| Annotation | Effect |
|---|---|
| `cert-manager.io/cluster-issuer: letsencrypt-prod` | Triggers cert-manager to request a certificate automatically |
| `nginx.ingress.kubernetes.io/ssl-redirect: "true"` | Redirects HTTP to HTTPS with 308 |
| `nginx.ingress.kubernetes.io/force-ssl-redirect: "true"` | Forces redirect even if behind another proxy |

### 8.3 — Watch the certificate being issued

```bash
# Watch certificate status
KUBECONFIG=~/.kube/config kubectl get certificate -n aml-lab -w
```

You will see it progress:

```
NAME               READY   SECRET              AGE
test-aml-lab-tls   False   test-aml-lab-tls    5s
test-aml-lab-tls   False   test-aml-lab-tls    30s
test-aml-lab-tls   True    test-aml-lab-tls    90s
```

`READY: True` means the certificate was issued. This takes **60–120 seconds** typically.

Press `Ctrl+C` once it shows `True`.

If it stays `False` after 3 minutes:

```bash
KUBECONFIG=~/.kube/config kubectl describe certificate test-aml-lab-tls -n aml-lab
KUBECONFIG=~/.kube/config kubectl describe challengerequest -n aml-lab
```

## Gate Verification

### Gate 1 — HTTPS returns 200 or 404 with valid Let's Encrypt certificate

```bash
curl -v https://test.aml-lab.amlsiem.com 2>&1 | grep -E "SSL|issuer|subject|HTTP|< HTTP"
```

Expected output includes:

```
* SSL connection using TLSv1.3
* Server certificate:
*  subject: CN=test.aml-lab.amlsiem.com
*  issuer: C=US; O=Let's Encrypt; CN=R11
* HTTP/2 200
```

The status can be 200 (nginx welcome page) or 404 (no content configured) — either is fine. What matters is the valid Let's Encrypt certificate.

---

### Gate 2 — HTTP returns 301 redirect to HTTPS

```bash
curl -v http://test.aml-lab.amlsiem.com 2>&1 | grep -E "< HTTP|Location"
```

Expected:

```
< HTTP/1.1 308 Permanent Redirect
< Location: https://test.aml-lab.amlsiem.com/
```

> Note: Nginx uses 308 (Permanent Redirect) not 301 for SSL redirects by default. 308 is semantically identical for this purpose — both tell the browser to redirect permanently to HTTPS.

---

### Gate 3 — Certificate shows correct issuer

```bash
echo | openssl s_client -connect test.aml-lab.amlsiem.com:443 -servername test.aml-lab.amlsiem.com 2>/dev/null | openssl x509 -noout -issuer -subject -dates
```

Expected output:

```
issuer=C=US, O=Let's Encrypt, CN=R11
subject=CN=test.aml-lab.amlsiem.com
notBefore=Jul 16 00:00:00 2026 GMT
notAfter=Oct 14 00:00:00 2026 GMT
```

`issuer` must show `Let's Encrypt`. `notAfter` shows the certificate is valid for 90 days — cert-manager auto-renews at 60 days.

## Step 9 — Template for Client Ingress Resources

Once gates pass, here is the standard Ingress template used for every client service in Sprints 1–7. Save this to `/opt/aml-siem/k8s/templates/ingress-template.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: SERVICE_NAME-ingress
  namespace: CLIENT_NAME
  annotations:
    kubernetes.io/ingress.class: nginx
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
spec:
  tls:
  - hosts:
    - SERVICE_NAME.CLIENT_NAME.amlsiem.com
    secretName: SERVICE_NAME-CLIENT_NAME-tls
  rules:
  - host: SERVICE_NAME.CLIENT_NAME.amlsiem.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: SERVICE_NAME
            port:
              number: SERVICE_PORT
```

**For ChemDry's Wazuh dashboard**, replace placeholders:
- `SERVICE_NAME` → `wazuh`
- `CLIENT_NAME` → `chemdry`
- `SERVICE_PORT` → `443`

This produces the URL `wazuh.chemdry.amlsiem.com` with automatic TLS.

## Common Issues and Fixes

| Problem | Cause | Fix |
|---|---|---|
| `EXTERNAL-IP <pending>` on Nginx service | ServiceLB not allocating IP | `sudo systemctl restart k3s` then wait 60s |
| Certificate stuck at `READY: False` | DNS not propagated yet | Wait 10–30 min, check `dig test.aml-lab.amlsiem.com` |
| `curl: (6) Could not resolve host` | DNS record not added or not propagated | Add DNS A record and wait |
| `curl: (7) Failed to connect` | Port 80/443 not open in GCP firewall | Add GCP firewall rules for ports 80 and 443 |
| ClusterIssuer `READY: False` | cert-manager can't reach Let's Encrypt | Check internet connectivity: `curl https://acme-v02.api.letsencrypt.org` |
| `too many certificates` error | Rate limit hit (50/domain/week) | Use `letsencrypt-staging` server for testing, switch to prod for final |
| HTTP returns 404 not 301 | ssl-redirect annotation missing | Confirm annotations are on the Ingress resource |
| Traefik still running | Old Traefik pods still alive | `kubectl delete deployment traefik -n kube-system` |
| Let's Encrypt staging cert | Wrong ClusterIssuer used | Confirm `cert-manager.io/cluster-issuer: letsencrypt-prod` in Ingress annotations |

### Let's Encrypt Rate Limits

Let's Encrypt limits certificate issuance to **50 certificates per domain per week**. During testing, use the staging server to avoid burning through this limit:

```yaml
# Staging ClusterIssuer (for testing only — cert is not trusted by browsers)
server: https://acme-staging-v02.api.letsencrypt.org/directory
```

Switch to `acme-v02.api.letsencrypt.org` (production) only for the final gate verification.
