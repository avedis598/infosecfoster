## Overview

This module installs K3s — a lightweight, production-grade Kubernetes distribution — on the GCP VM. K3s is the deployment engine for every client-facing AML-SIEM service. Understanding why K3s exists alongside Docker is critical before touching a single command.

### The Two-Track Rule — Read This First

The AML-SIEM platform uses two parallel deployment methods that serve completely different purposes:

| Track | Tool | When Used | Who Sees It |
|---|---|---|---|
| **Lab track** | Docker Compose | Development and iteration only | Engineers only |
| **Client track** | K3s Kubernetes | Every client deployment | Clients |

**Docker Compose** is your scratchpad. You use it to get a service running quickly, test configuration, debug issues, and iterate fast. It lives in `/opt/aml-siem/compose/`. It never gets deployed to a client.

**K3s manifests** are the real product. Every service you build in Compose must have a matching Kubernetes manifest before the module is considered complete. The manifest lives in `/opt/aml-siem/k8s/`. This is what `deploy-client.sh` applies when onboarding a client.

The promotion rule is absolute: a module is not complete until both the Compose config AND the K3s manifest exist, are both tested, and both committed to Git.

### Why K3s Instead of Full Kubernetes?

Full Kubernetes (kubeadm) requires a minimum of 3 control plane nodes, significant RAM overhead (~2GB just for the control plane), and complex certificate management. K3s packages the full Kubernetes API into a single binary under 100MB, runs comfortably on a 4GB RAM server, handles certificate rotation automatically, and supports the same `kubectl` commands and Helm charts as full Kubernetes. When you need to scale a client deployment to multiple nodes, you add worker nodes to K3s — the process is straightforward.

## Step 2 — Pre-Installation Checks

Before installing K3s, confirm the VM meets the minimum requirements and that there are no port conflicts.

### 2.1 — Check Available Resources

```bash
# RAM — K3s needs at least 512MB free, recommend 2GB+ for AML-SIEM
free -h

# Disk — K3s needs at least 1GB, container images need much more
df -h /

# CPU
nproc
```

Minimum acceptable values:

| Resource | Minimum | Recommended for AML-SIEM |
|---|---|---|
| RAM | 512MB free | 16GB+ total |
| Disk | 10GB free | 100GB+ |
| CPU | 1 core | 4+ cores |

### 2.2 — Check Port Availability

K3s uses several ports. Confirm none are already in use:

```bash
# Check ports K3s will use
sudo ss -tlnp | grep -E ':6443|:10250|:10251|:10252|:2379|:2380'
```

Expected output: nothing — all ports should be free. If any are in use, identify and stop the conflicting service before proceeding.

### 2.3 — Disable Firewall Temporarily During Install

UFW can interfere with K3s networking during installation. Disable it temporarily — you will re-enable it after:

```bash
sudo ufw disable
```

> You will re-enable UFW in Step 8 after K3s networking is fully configured.

## Step 3 — Install K3s

K3s is installed via a single official install script. This script downloads the K3s binary, installs it as a systemd service, and configures all components automatically.

```bash
curl -sfL https://get.k3s.io | sh -
```

This command:
- Downloads the K3s binary (~100MB)
- Installs K3s as a systemd service called `k3s`
- Starts the K3s server automatically
- Installs `kubectl`, `crictl`, and `ctr` as bundled tools
- Generates TLS certificates for the cluster
- Creates the kubeconfig file at `/etc/rancher/k3s/k3s.yaml`

The install takes 1–3 minutes depending on network speed. You will see output like:

```
[INFO]  Finding release for channel stable
[INFO]  Using v1.xx.x+k3s1 as release
[INFO]  Downloading hash ...
[INFO]  Downloading binary k3s
[INFO]  Verifying binary download
[INFO]  Installing K3s to /usr/local/bin/k3s
[INFO]  Creating /usr/local/lib/systemd/system/k3s.service
[INFO]  systemd: Starting k3s
```

### 3.1 — Verify K3s Service Is Running

```bash
sudo systemctl status k3s
```

Expected output:

```
● k3s.service - Lightweight Kubernetes
     Loaded: loaded (/etc/systemd/system/k3s.service; enabled)
     Active: active (running)
```

Check K3s version:

```bash
k3s --version
```

Expected output:

```
k3s version v1.xx.x+k3s1 (xxxxxxxx)
go version go1.xx
```

## Step 4 — Configure kubeconfig for Engineer Access

By default, K3s writes its kubeconfig to `/etc/rancher/k3s/k3s.yaml` which is only readable by root. You need to make it accessible to your engineer user so you can run `kubectl` without `sudo`.

### 4.1 — Copy kubeconfig to Engineer Home Directory

```bash
# Create .kube directory in your home
mkdir -p ~/.kube

# Copy the K3s kubeconfig
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config

# Set ownership to your user
sudo chown $USER:$USER ~/.kube/config

# Set correct permissions — kubeconfig must not be world-readable
chmod 600 ~/.kube/config
```

### 4.2 — Set KUBECONFIG Environment Variable

Add the KUBECONFIG path to your shell profile so it is set automatically on every login:

```bash
echo 'export KUBECONFIG=~/.kube/config' >> ~/.bashrc
source ~/.bashrc
```

Verify the environment variable is set:

```bash
echo $KUBECONFIG
```

Expected:

```
/home/amlsiem/.kube/config
```

### 4.3 — Verify kubeconfig Content

The kubeconfig file tells kubectl where to find the cluster and which credentials to use:

```bash
cat ~/.kube/config
```

You should see a YAML file with sections for `clusters`, `users`, and `contexts`. The server address will be `https://127.0.0.1:6443` — this is the K3s API server listening on localhost.

## Step 5 — Install kubectl

K3s bundles its own kubectl at `/usr/local/bin/kubectl` — it was installed in Step 3. Verify it is accessible:

```bash
which kubectl
kubectl version --client
```

Expected:

```
/usr/local/bin/kubectl
Client Version: v1.xx.x
```

If `kubectl` is not found, install it explicitly:

```bash
# Only run this if kubectl was not found above
sudo ln -sf /usr/local/bin/k3s /usr/local/bin/kubectl
```

Or install the official standalone kubectl:

```bash
curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
rm kubectl
```

## Step 7 — Create AML-SIEM Namespaces

Kubernetes namespaces provide logical isolation between environments and clients. Two namespaces are needed now:

| Namespace | Purpose |
|---|---|
| `aml-lab` | All development and testing. Engineers can break things here freely without affecting anything else. |
| `aml-client-template` | The reference template that `deploy-client.sh` clones when onboarding a new client. Never deployed directly to a client — it is the master copy. |

### 7.1 — Create the Namespaces

```bash
kubectl create namespace aml-lab
kubectl create namespace aml-client-template
```

### 7.2 — Add Labels to Namespaces

Labels make namespaces easier to filter and manage as the platform grows:

```bash
kubectl label namespace aml-lab \
  environment=lab \
  managed-by=amlak \
  purpose=development

kubectl label namespace aml-client-template \
  environment=template \
  managed-by=amlak \
  purpose=client-reference
```

### 7.3 — Verify Namespaces Exist

```bash
kubectl get namespaces
```

Expected output includes:

```
NAME                   STATUS   AGE
aml-lab                Active   Xs
aml-client-template    Active   Xs
default                Active   Xm
kube-system            Active   Xm
kube-public            Active   Xm
kube-node-lease        Active   Xm
```

## Step 9 — Re-enable UFW with K3s Rules

K3s requires specific ports to be open for its internal networking. Re-enable UFW and add the necessary rules:

```bash
# Re-enable UFW
sudo ufw enable

# K3s API server — used by kubectl
sudo ufw allow 6443/tcp comment 'K3s API server'

# Flannel VXLAN — K3s internal pod networking
sudo ufw allow 8472/udp comment 'K3s Flannel VXLAN'

# Kubelet metrics
sudo ufw allow 10250/tcp comment 'K3s kubelet metrics'

# Allow all traffic on the K3s network interfaces (pod-to-pod comms)
sudo ufw allow in on cni0
sudo ufw allow in on flannel.1
sudo ufw allow in on lo

# Verify
sudo ufw status verbose
```

> Port 6443 is the only port that needs to be open externally (for kubectl from your Mac in the future). The other ports are for internal cluster communication.

## Step 10 — Test Apply and Delete a Manifest

This step verifies the engineer can independently apply and delete Kubernetes resources — which is the core skill needed for every sprint.

### 10.1 — Create a Test Manifest File

```bash
cat > /tmp/test-manifest.yaml << 'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: aml-test-pod
  namespace: aml-lab
  labels:
    app: aml-test
    created-by: m0.3-gate-test
spec:
  containers:
  - name: test-container
    image: nginx:alpine
    ports:
    - containerPort: 80
  restartPolicy: Never
EOF
```

### 10.2 — Apply the Manifest

```bash
kubectl apply -f /tmp/test-manifest.yaml
```

Expected:

```
pod/aml-test-pod created
```

### 10.3 — Verify the Pod Is Running

```bash
kubectl get pod aml-test-pod -n aml-lab
```

Wait until STATUS shows `Running`:

```
NAME           READY   STATUS    RESTARTS   AGE
aml-test-pod   1/1     Running   0          30s
```

If it shows `ContainerCreating` — wait 30–60 seconds for the image to pull and run:

```bash
# Watch until Running
kubectl get pod aml-test-pod -n aml-lab -w
```

Press `Ctrl+C` once it shows Running.

### 10.4 — Describe the Pod (Optional but Good Practice)

```bash
kubectl describe pod aml-test-pod -n aml-lab
```

This shows the full event log for the pod — useful for debugging in future sprints.

### 10.5 — Delete the Test Pod

```bash
kubectl delete -f /tmp/test-manifest.yaml
```

Expected:

```
pod "aml-test-pod" deleted
```

Confirm it is gone:

```bash
kubectl get pods -n aml-lab
```

Expected:

```
No resources found in aml-lab namespace.
```

### 10.6 — Clean Up Test File

```bash
rm /tmp/test-manifest.yaml
```

## Common Issues and Fixes

| Problem | Cause | Fix |
|---|---|---|
| `kubectl: command not found` | K3s didn't symlink kubectl | `sudo ln -sf /usr/local/bin/k3s /usr/local/bin/kubectl` |
| `connection refused` on port 6443 | K3s still starting | Wait 60s then retry — `sudo systemctl status k3s` |
| Node shows `NotReady` | K3s initialising | Wait 2–3 minutes — run `kubectl get nodes -w` to watch |
| `permission denied` on kubeconfig | Wrong file permissions | `sudo chown $USER:$USER ~/.kube/config && chmod 600 ~/.kube/config` |
| `Unable to connect to server` | kubeconfig not set | `export KUBECONFIG=~/.kube/config` then `source ~/.bashrc` |
| Pod stuck in `ContainerCreating` | Image pulling slowly | Wait — run `kubectl describe pod <name> -n aml-lab` to see progress |
| UFW blocking cluster traffic | Firewall rules missing | Run all `ufw allow` commands in Step 9 |
| `namespace "aml-lab" already exists` | Namespace already created | Safe to ignore — run `kubectl get namespaces` to confirm |
| K3s install fails mid-way | Network timeout | Re-run `curl -sfL https://get.k3s.io \| sh -` — install is idempotent |
